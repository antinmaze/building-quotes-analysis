Demarrage en trois etapes depuis le checkout
==========================================

Les trois commandes sont independantes. Aucune etape ne lance la suivante.
Les etapes 2 et 3 utilisent un espace prive dedie a un corpus, par exemple
results/nouveau-corpus. Elles ne modifient pas outputs/compet.xlsx ni son registre.
Installer d'abord le projet (instructions ci-dessous), puis activer .venv.
La commande infra est un lanceur du Bicep existant, pas une nouvelle topologie.
Elle requiert Azure CLI avec Bicep, une session az login et les droits de
deploiement/RBAC pour le groupe cible. Elle n'installe pas ces outils.

Etape 1 - Infrastructure et configuration
----------------------------------------

Si le fichier prive infra/main.parameters.json existe, le conserver et en
verifier les valeurs. Sinon copier le modele public :
  test -e infra/main.parameters.json || \
    cp infra/main.parameters.example.json infra/main.parameters.json

Renseigner la souscription, l'object ID Entra de l'utilisateur operateur,
la region, les noms de comptes uniques et l'horodatage UTC. Les UUID nuls
et REPLACE_WITH_UTC_TIMESTAMP du modele sont des exemples a remplacer.
Le modele utilise les services et le deploiement Global Standard deja definis
dans infra/ ; cela peut traiter les donnees hors de la region du compte.
Verifier la disponibilite du modele, le quota, les couts et les contraintes de
residence avant d'autoriser le deploiement. L'operateur RBAC est un utilisateur,
pas un service principal. Ne pas mettre de cles dans le fichier de parametres.

Previsualisation, sans creation de ressources :
  devis-mngt infra --parameters infra/main.parameters.json \
    --settings results/azure-settings.json --create-resource-group

Si le groupe existe, le what-if est execute. S'il est absent, la commande
annonce seulement sa creation necessaire : ce n'est PAS un what-if complet.
Le groupe n'est pas cree pendant cette previsualisation.

Apres validation des risques/couts, autoriser le deploiement :
  devis-mngt infra --parameters infra/main.parameters.json \
    --settings results/azure-settings.json --create-resource-group --apply

Avec --apply, le groupe absent est cree avant le what-if des ressources.
En cas d'echec ulterieur, ce groupe peut donc rester cree ; aucune suppression
automatique n'est effectuee. Sans --create-resource-group, un groupe absent
est refuse. Un groupe existant de region differente est refuse.
Le what-if est obligatoire avant le deploiement et toute suppression detectee
le bloque. Aucun deploiement n'est lance sans --apply.
Apres succes, les endpoints, le tenant, le deploiement et la revision du modele
sont enregistres dans le fichier --settings (JSON prive avec checksum).
Un fichier de configuration existant n'est jamais ecrase : utiliser un autre
chemin pour un nouveau deploiement. La propagation des droits RBAC peut demander
quelques minutes. Cette etape ne lance aucune analyse de PDF.

Etape 2 - Integration d'un nouveau PDF
-------------------------------------

Controler localement un PDF, sans Azure ni ecriture dans l'espace de travail :
  devis-mngt integrate --input /chemin/devis.pdf \
    --workspace results/nouveau-corpus

Autoriser ensuite son analyse OCR/IA :
  devis-mngt integrate --input /chemin/devis.pdf \
    --workspace results/nouveau-corpus --settings results/azure-settings.json \
    --max-ocr-pages 50 --max-llm-calls 100 --allow-cloud

--settings peut etre omis si les variables Azure sont deja chargees.
Repeter cette commande pour chaque PDF a ajouter au meme corpus.
Chaque fichier a son cache et son resultat ; les autres fichiers integres
ne sont pas remplaces. Reintegrer le meme chemin actualise son resultat
(y compris un echec), sans ajouter un doublon de source. Les etapes de cache
compatibles sont reutilisees. Les limites s'appliquent a chaque execution,
pas a un budget cumule. Le PDF source doit rester hors du workspace.
Les erreurs documentaires, y compris les PDF illisibles, sont enregistrees
pour l'etape 3. Une limite atteinte est aussi enregistree et retourne le code 2 ;
une reprise avec un plafond adapte reutilise les caches disponibles.
Un chemin inexistant ou un format autre que PDF est refuse sans integration.
Cette etape ne produit pas encore le classeur consolide.

Etape 3 - Consolidation et recuperation des rapports, sans Azure
--------------------------------------------------------------

  devis-mngt consolidate --workspace results/nouveau-corpus

La sortie JSON fournit les chemins absolus et les SHA256 des deux classeurs :
- prices.xlsx : base de prix, donnees brutes, tracabilite, documents et controles ;
- errors.xlsx : documents en erreur/non-devis/sans lignes, lignes a verifier
  et ecarts de couverture OCR.
Un rapport sans anomalie conserve les en-tetes, il n'est pas absent.
Les lignes non valides restent hors de la base de prix.
Les exemplaires identiques peuvent etre regroupes en base sans perdre leurs
occurrences source ; des prix differents ne sont pas fusionnes.
Chaque consolidation cree une generation sous workspace/reports/ et conserve
les rapports precedents. workspace/latest-report.json (enveloppe avec checksum)
reference la derniere paire publiee. Tant que l'etape 3 n'est pas relancee,
les rapports ne refletent pas les nouvelles integrations.
Une erreur de generation ne remplace pas le manifeste de la derniere paire
publiee. La commande ne copie rien vers compet.xlsx et n'a besoin ni de
configuration Azure ni d'acces reseau. Les erreurs documentaires retournent 1 ;
une base sans ligne acceptee retourne 3. Examiner aussi les lignes a verifier
meme lorsque le code de sortie est 0.
Un verrou operation.lock empeche les operations simultanees dans le workspace.
En cas d'interruption, verifier qu'aucun traitement ne tourne avant de retirer
manuellement ce verrou ; ne jamais contourner un verrou actif.
Sauvegarder le workspace entier pour conserver cache, resultats et rapports.

Analyser de nouveaux devis PDF (outil reutilisable)
=================================================

Le moteur applicatif est dans src/devis_mngt/. Il ne depend ni des devis
historiques, ni de compet.xlsx, ni des scripts de selection des anciennes vagues.
Les scripts prepare_wave*, select_wave2 et verify_pilot sont des outils de
campagne historique, pas des prerequis pour analyser de nouveaux fichiers.

Installation locale (Python >= 3.11) :
  python3 -m venv .venv
  . .venv/bin/activate
  python -m pip install -e .

1. Inventorier un nouveau dossier, sans Azure :
  devis-mngt inventory --input /chemin/nouveaux-devis

2. Configurer les ressources Azure existantes :
  # Seulement si .env n'existe pas encore (ne pas ecraser la configuration) :
  test -e .env || cp .env.sample .env
  # Renseigner les endpoints et le deploiement dans .env, puis :
  set -a; . ./.env; set +a

Variables requises : AZURE_DOCUMENT_INTELLIGENCE_ENDPOINT,
AZURE_OPENAI_ENDPOINT, AZURE_OPENAI_DEPLOYMENT.
AZURE_TENANT_ID est optionnel pour preciser le tenant de la session az login.
Les cles optionnelles sont decrites dans .env.sample. L'application ne charge
pas .env automatiquement. Seule la commande infra --apply cree des ressources ;
run et wave utilisent
la meme configuration externe : aucun abonnement ou endpoint historique
n'est impose. Le modele deploye doit etre compatible avec les requetes
structurees et les parametres du client ; renseigner sa revision dans
AZURE_OPENAI_MODEL_REVISION pour identifier correctement les caches.

3. Apres accord sur les appels facturables, analyser un PDF ou un dossier :
  devis-mngt run --input /chemin/nouveaux-devis \
    --output outputs/nouveaux-devis.xlsx \
    --cache .devis-cache/nouveaux-devis --log-dir logs/nouveaux-devis \
    --pdf-only --max-ocr-pages 50 --max-llm-calls 100 --allow-cloud

Les plafonds sont des exemples par execution, pas un budget en euros.
Sans --allow-cloud, aucun traitement Azure n'est lance. Avec --pdf-only,
seuls les PDF sont examines ; les sous-dossiers 00_ARCHIVES sont exclus.
Un chemin de PDF unique est aussi accepte comme --input.
Le classeur, le cache et les journaux doivent rester hors du dossier source.
Un nouveau corpus doit utiliser un cache et une sortie dedies : cette commande
ne fusionne pas automatiquement les nouveaux resultats avec compet.xlsx.
Pour ajouter des PDF au meme corpus, les placer dans le dossier d'entree
et relancer la meme commande : les etapes en cache sont reutilisees pour les
sources et configurations inchangees, et le classeur couvre les fichiers
actuellement presents dans cette entree. Garder les anciens PDF dans ce dossier
si leurs lignes doivent rester dans ce classeur. Une limite atteinte arrete
le run avec erreur et sauvegarde results.partial.json ; relancer avec un
plafond adapte reprend les etapes cachees. Il n'y a pas de contournement
automatique des limites ni de garantie de zero appel lors d'une reprise.

4. Regenerer l'Excel sans nouvel appel Azure :
  devis-mngt export --results .devis-cache/nouveaux-devis/results.json \
    --output outputs/nouveaux-devis.xlsx --log-dir logs/nouveaux-devis

Le classeur contient les sept champs metier demandes, la provenance des lignes,
les donnees brutes, les documents ignores et les lignes a verifier.
Le statut extracted signifie qu'une extraction est disponible, pas que toutes
les lignes sont validees : seules les lignes admises par les controles vont
dans Base de prix. Les prix differents restent distincts. Aucune valeur
manquante ou ambigue n'est remplacee silencieusement par une estimation.
Les erreurs documentaires restent dans l'audit et produisent un code non nul.
Codes de sortie : 0 = base avec donnees acceptees, 1 = erreur documentaire,
2 = configuration/usage/limite, 3 = aucune donnee acceptee.
L'export hors ligne exige results.json d'un run termine ; un fichier partiel
ne represente pas l'ensemble du corpus. Toujours examiner A verifier et
Couverture avant d'utiliser la base de prix.

Controle hors ligne du code, sans documents historiques ni Azure :
  python -m unittest discover -s tests -q

Ne pas publier .env, devis/, outputs/, results/, logs/ ou .devis-cache/.
Ne pas lancer les scripts historiques pour un nouveau corpus.

Conserver et reprendre le corpus actuel
======================================

Le code reutilisable et le corpus historique restent dans ce meme projet.
Aucun deplacement, renommage ou nettoyage des donnees privees n'est necessaire.
Conserver les chemins existants : les manifestes et caches referencent les
sources par chemin et SHA256. Un clone Git seul ne restaure pas le travail local.

Elements a sauvegarder ensemble sur un stockage prive :
- devis/ : PDF originaux, jamais modifies par l'extraction ;
- outputs/compet.xlsx ET outputs/compet.campaign.json : paire inseparable ;
- .devis-cache/ : tous les caches et marqueurs de selection des anciennes vagues ;
- results/ : selections approuvees, corrections et decisions de revue ;
- logs/ : historique des traitements ;
- outputs/backup-compet-import-devis-*/ : sauvegardes avant consolidation ;
- les autres classeurs et registres de outputs/ : campagnes de reprise et rapports.
Garder .env separement dans une sauvegarde protegee s'il contient des cles.
La sauvegarde doit se faire hors traitement, pour obtenir des fichiers coherents.
Les sauvegardes presentes dans outputs/ sont locales : elles ne protegent pas
contre une perte du disque. Aucun de ces fichiers prives ne doit etre force-ajoute
a Git. Conserver aussi PLAN-TRAITEMENT.md comme historique prive ; ce n'est pas
le mode d'emploi generique ni un etat a jour des traitements.

Les commandes run et export refusent de remplacer un classeur accompagne
d'un registre .campaign.json ou d'un verrou .xlsx.lock, y compris via un lien
symbolique. La publication transactionnelle de campagne reste autorisee :
elle reconstruit toutes les vagues, controle le SHA du classeur, puis met a jour
le classeur et son registre avec un journal de reprise.
Ne pas supprimer le registre ou le verrou pour contourner cette protection.
Un verrou peut signaler un traitement actif ou interrompu : verifier avant reprise.

Pour poursuivre les devis actuels :
1. Partir du rapport prive outputs/pdf-non-traites-final-2026-11-03.xlsx et
   des corrections consignees dans results/, sans retraiter tous les PDF.
2. Preserver les exclusions explicites et verifier les motifs techniques :
   certains anciens libelles "ecarte" correspondent a des PDF bloques.
3. Preparer une selection ciblee avec les chemins/SHA et pages retenues.
   Une reprise deja reussie ne doit pas etre relancee automatiquement.
4. Appliquer les corrections confirmees au seul PDF concerne et conserver
   sa provenance avant reintegration dans le cumulatif.
5. Si Azure est requis, reconstruire/configurer les ressources avant lancement.
   Le registre verifie aussi l'identite de configuration : de nouveaux endpoints
   ou un nouveau modele peuvent exiger une migration controlee, avec sauvegarde.
   Ne pas modifier le JSON a la main ni reutiliser un cache sous une fausse identite.

Le precontrole d'une selection deja approuvee est local :
  devis-mngt wave --manifest results/SELECTION-EXISTANTE.json --input devis
Remplacer SELECTION-EXISTANTE par le manifeste voulu, jamais par un choix arbitraire.
Sans --allow-cloud, cette commande ne traite rien et ne change pas le cumulatif.
Elle verifie la selection, pas la disponibilite Azure ni toute la campagne.
Ne pas executer run --input devis --output outputs/compet.xlsx :
run n'est pas une fusion de campagne et cette destination est desormais protegee.

Pour un nouveau corpus, utiliser par exemple /chemin/nouveau-corpus comme entree,
.devis-cache/nouveau-corpus comme cache, logs/nouveau-corpus comme journaux et
outputs/nouveau-corpus.xlsx comme sortie. Cela ne touche pas au corpus actuel.
Ne jamais lancer deux traitements utilisant le meme cache ou la meme campagne.

Perimetre du commit
===================

Le commit doit contenir le moteur src/, les tests generiques tests/, les outils
reutilisables scripts/, la configuration et la documentation technique.
Les scripts specifiques aux anciennes campagnes et leur test d'instantane
test_wave_preparation.py restent disponibles localement mais sont ignores par
Git. Ils contiennent des decisions de selection et des references au corpus :
ne pas les publier, meme si leur extension est .py. Les conserver dans la
sauvegarde privee, avec PLAN-TRAITEMENT.md et les donnees de campagne.
scripts/evaluate_local_ocr.py reste un outil generique et fait partie du code.

Avant de preparer l'index, verifier aussi les nouveaux fichiers non ignores :
  python scripts/check_public_files.py --include-untracked
  python -m unittest discover -s tests -q
  git diff --check

Apres une selection explicite des fichiers du commit, verifier l'index :
  python scripts/check_public_files.py --staged
Le controle refuse les fichiers historiques connus meme s'ils sont force-ajoutes.
Il controle les chemins, pas le contenu : relire le diff avant publication.
Les tests de campagne prives peuvent s'executer localement ; ils ne sont pas
necessaires aux tests generiques du code publie. Ne pas utiliser git add -f
pour inclure des documents, caches, rapports, journaux ou scripts historiques.

Infrastructure et historique du pilote
=====================================

This directory contains deployment-ready Bicep for the approved local pilot.

Scope:
- Existing resource group: rg-devis-mngt
- Document Intelligence S0 account: di-devis-mngt-dev-ed16
- Azure OpenAI S0 account: aoai-devis-mngt-dev-ed16
- Global Standard deployment: devis-extraction, gpt-5-mini, version 2025-08-07, capacity 50
- Two user-scoped data-plane role assignments for the verified operator object ID

This scaffold does not deploy resources and does not make paid calls.

GitHub Actions (recommended):
- Offline checks run on pushes and pull requests; no Azure credentials or documents.
- Deploy Azure AI pilot runs only via workflow_dispatch on main by the repository owner.
- The azure-pilot environment accepts deployments from main only.
- Read the exact OIDC sub_claim_prefix using:
  gh api repos/OWNER/REPO/actions/oidc/customization/sub
  Recent repositories use repo:OWNER@OWNER_ID/REPO@REPO_ID. Pass that prefix as
  githubSubjectPrefix to the bootstrap template, not a guessed repository name.
- Federated identity subject: PREFIX:environment:azure-pilot.
- Environment secrets: AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID,
  AZURE_OPERATOR_OBJECT_ID. These identifiers are not passwords.
- Environment variables: AZURE_RESOURCE_GROUP and AZURE_LOCATION.
- infra/github-oidc.bicep bootstraps the identity once using an authorized Azure operator.
- GitHub has Cognitive Services Contributor on this resource group, plus conditional
  RBAC administration limited to two data-plane roles and the specified operator.
- infra/pilot.bicep deploys at resource-group scope; no subscription-wide grant.
- Preview is mandatory before deploy. No documents are processed or uploaded by CI.
- Never publish infra/main.parameters.json, .env, quotes, spreadsheets or OCR caches.

Non-mutating checks:
  az bicep build --file infra/main.bicep --stdout > /dev/null
  az deployment sub what-if --subscription "$AZURE_SUBSCRIPTION_ID" --location francecentral --template-file infra/main.bicep --parameters @infra/main.parameters.json

Future deployment, only after explicit approval:
  az deployment sub create --subscription "$AZURE_SUBSCRIPTION_ID" --location francecentral --template-file infra/main.bicep --parameters @infra/main.parameters.json

The model name and version are infrastructure parameters. A model change is
not assumed to be plug-compatible: revalidate
structured-output support, API version, response behavior, and application request
parameters. The application omits temperature and legacy max_tokens, which are not
supported by gpt-5-mini, and allows 300 seconds per request. The model revision
marker invalidates extraction caches without repeating cached OCR.
Extraction uses low reasoning effort. Blocking review reasons are separated from
informational comments; line-specific ambiguities must not reject unrelated rows.
Valid French dates with two-digit years can corroborate the extracted year.
Simple French decimal quantities (e.g. 1,00) are normalized to 1.00 without
calculating missing values; ambiguous separators remain validation errors.
The local pilot workbook is written to results/prix-samples.xlsx; results/ is private.
Each CLI run/export appends a private JSONL journal in logs/ (override: --log-dir):
logs/prix-samples.events.jsonl. Follow it with:
  tail -f logs/prix-samples.events.jsonl
Each new event also appends one physical row to logs/prix-samples.events.csv
(UTF-8, semicolon separator, headers, escaped line breaks), readable in VS Code.
The JSONL is the canonical journal; CSV contains the same new events, with
spreadsheet formula prefixes escaped. CSV does not backfill older JSONL events.
Events include UTC timestamp, run ID, sequence, source filename/SHA256, OCR and
extraction start/end/cache hits/durations, failures, per-line review reasons with
source pages/excerpts, extracted metadata and final export counts.
Line indexes refer to extraction order within a source document, not sorted Excel rows.
Accepted line counts precede exact deduplication; accepted_rows is the final base size.
Offline exports reconstruct document/line findings with retrospective=true and do not
invent historical OCR/inference times. The event timestamp is the observation time.
Journal errors are surfaced; raw SDK error payloads and credentials are not logged.
Journals contain private quote data, are owner-readable/writable, and stay local.

Quality routing (rules-3):
Scores are deterministic quality indicators, NOT calibrated AI probabilities.
Base de prix accepts only lines without blockers and with score >= 0.90.
Fully corroborated rows score 1.00; interpreted units cap quality at 0.85,
unless corroborated by a single explicit PU row, matching quantity x price/total,
and a narrow work rule: explicit forfait, explicit "Le Ml", or countable equipment
with an integer quantity. Those units score 0.95 and retain interpretation warnings
and the exact rule in the audit. Surface units without adequate proof remain 0.85.
Other blocking issues cap quality at 0.60. A price/evidence/HT/arithmetic
problem caps both price and overall scores at 0.05, regardless of other fields.
All rejected occurrences go exclusively to A verifier, not to the base.
Tracabilite remains the full audit (both destinations) with score and destination.
The seven template columns remain first; numeric quality/price/threshold columns
are appended to the base, audit and review sheets. The workbook opens on the base.
Filename project names override a billing name only if the project name is supported
by the actual document text or by the existing cross-document beneficiary evidence.
A filename/content client mismatch otherwise blocks the affected source explicitly.
For multi-block PDFs, the user-confirmed identity rules keep the normalized company
and project client from the first processed block (pages 1-2 when it has lines).
Later company and client names do not reject the merge and remain in line audit
warnings. A missing first company or client stays missing. Other quality checks,
including raw reading conflicts and filename corroboration, remain unchanged.
The merge policies invalidate aggregate normalization caches
without discarding cached OCR or individual block responses.

PO-confirmed surface rule (surface-quantity-1):
An explicit "Surface X m2" in the source with billed quantity 1 is a Forfait
for X m2, not a per-m2 price; append "pour X m²" to label and signature.
A billed quantity equal to that surface stays per m2. No division, multiplication
or replacement of the source PU is performed. Contradictory explicit units,
multiple distinct surfaces and ambiguous quantities are not resolved by this rule.
Surface 1 m2 with quantity 1 is treated per m2, not guessed as a forfait.
The interpreted unit may score 0.95 only with the usual explicit PU table anchor
and corroborating quantity x PU / total; other blockers still apply.

Label rules (labels-1), independent of the expected workbook:
Prefer complete short source descriptions (up to 160 characters), remove known
room-heading contamination and model-added unit/supply boilerplate absent from
the source. Preserve source supply/installation scope, dimensions and technical
features. Long descriptions keep their synthesized technical label, not a cut-off
first line copied from the reference. Surface forfaits retain "pour X m²".
The pre-rule label is retained in the audit; prices, signatures and attribution
are not changed by label cleanup. Options are not appended twice when already
present in the label. Expected labels are used for comparison only.

Labour labels are qualified from their numbered parent section in OCR tables,
or the following local subtotal before the next section/table boundary. The
section and exact OCR row evidence are exported in the audit. Generic labour
with an anchored but unresolved section is sent for review. Context is also a
deduplication boundary: identical labour names in different sections do not merge.
No price, quantity or unit is inferred from this description context.

Company display names use the company segment of the structured filename only
when its tokens are corroborated by both the raw issuer identity and exact OCR
company evidence. Uncorroborated filename hints are reported, not substituted.
The original company identity remains in the audit.

User-approved presentation policy: all new run results use Forfait in the seven
business columns. The price is the source line total HT, or quantity x source PU
when the total is absent; an already forfait-priced PU is usable without quantity.
Otherwise the forfait price is left empty and the occurrence requires review.
Source arithmetic inconsistencies still block acceptance. Designations append
the billed quantity and source unit (surface/length/etc. when justified), retaining
known work dimensions without inventing missing ones. The audit retains source
PU, quantity, total, raw and normalized source units, and conversion policy.
Each quantity/scope is a deduplication boundary. No section subtotal is substituted
for a priced line. This supersedes the earlier per-m2 presentation rule, not the
faithful source reading. Existing legacy batches keep source presentation unless
their lines explicitly enable export_forfait.

PO feedback supersedes the all-forfait presentation policy: new runs enable
export_unit_prices and disable export_forfait. Keep source PU and source units;
convert forfait to per-m2/per-ml only for a single explicitly labelled surface or
length, positive, with billed quantity exactly 1. Divide source forfait PU by that
measure. Ambiguous measured forfaits require review. Product dimensions (doors,
duct lengths without an explicit metric label) are not construction take-offs.
Do not infer area from width x height. Unmeasured forfaits remain forfaits.
Business designations use complete raw OCR descriptions plus attested section
context. The Données brutes sheet preserves every raw designation, unit, PU,
quantity and line total. Audit states the conversion formula and source PU;
Excel retains full division precision, displaying currency to two decimals.

User-confirmed exception: "Tri, gestion, évacuation et valorisation ou élimination
des déchets" is a Forfait. Export its line total HT (or quantity x PU HT when total
is absent), never the source PU as a per-tonne/per-m2 price. Preserve the complete
raw label and source figures. This explicit user decision resolves the inferred
unit doubt only; missing price, arithmetic and other source blockers still apply.

User-approved VMC packaging: Resist'r RE2020 D82 Iso.25 PVC/intissé 10ml,
D127 6ml and D160 6ml use U = one packaged length. Keep source PU and fractional
billed quantities unchanged. Display the product length explicitly in the label;
never interpret the source PU as per-metre. This narrow rule resolves only the
unit uncertainty for these exact product descriptions; raw OCR remains unchanged.

LOCAL-FIRST / LOCAL OCR (opt-in, no automatic cloud permission)
Python dependencies: install the project with pip install -e .
macOS native prerequisites: brew install tesseract tesseract-lang ghostscript
Tesseract must list fra in tesseract --list-langs. OCRmyPDF is installed by pip.

Offline diagnosis on the pilot (choose a new report path for each run):
  devis-mngt plan --input devis-sample --output results/diagnostic-ocr-local.json \
    --cache .devis-cache/local-pilot --local-ocr
This command never instantiates Azure clients. It does NOT create a validated
price database. --local-ocr runs OCRmyPDF/Tesseract fra on pages rejected by the
native reader, using a separate searchable PDF in a private cache. Originals
remain unchanged. Private logs retain engine errors/warnings. Missing tools or
failed OCR are explicit failures, not successful text extraction or cloud calls.
Force rasterization is applied only to rejected pages of the copy at >=300 dpi;
rotation/deskew are enabled. This may change the appearance of the COPY.
Text recognition is not equivalent to correct table/price-column reconstruction.
Only missing/short/garbled native text or a substantial image triggers Tesseract.
A native table geometry failure alone does NOT trigger rasterization of correct
digital text. The pilot stress test showed that forcing OCR on digital text can
change digits; retaining native text is essential.

After separate authorization only, run supports:
  --local-first --local-ocr --pdf-only --exclude-dir 00_ARCHIVES
Local table acceptance requires explicit description/quantity/PU HT/total headers,
numeric rows with quantity x PU within .02 of total, and no decimal price outside
the accepted grids. Otherwise only the affected original page is sent to Azure.
Page numbers, table spans and coordinates remain linked to the original.
No local text/page truncation; no automatic guessing of missing units or columns.
No automatic final-version selection or non-quote deletion is implied.

Full Azure OCR caches are reused before local OCR. Local searchable PDFs and
individual Azure page responses are cached separately for restart/reuse.
Normalization retains full source excerpts and row IDs in its LLM payload.
The validated normalization cache version is works-2.
llm_usage journal events include provider usage (input/output/reasoning details
where supplied). --max-ocr-pages N and --max-llm-calls N stop BEFORE exceeding
the per-run counters; interrupted results go to results.partial.json in the cache.
These are not euro limits or cross-run credit accounting. Calls attempted count
even on failure. LLM SDK auto-retries are disabled when limits are configured.
Azure DI transport retries can still occur; do not treat counters as billing proof.

PRIVATE BATCH PREPARATION AND SUBSCRIPTION COST WATCH

Restores original page numbers in OCR page texts, raw page objects and table

Selected-page OCR caches and client-context normalization keys are separate from

Default dedicated cache .devis-cache/compet-wave-1 is pinned to the approved

Each later approved manifest uses its own dedicated cache, but the SAME output.
The adjacent private compet.campaign.json journal stores every wave's structured

Keep this journal with the workbook: never delete it to force an overwrite.
An unrelated or manually modified workbook is refused before inference.
Replaying an unchanged wave skips successful documents; paused/error documents
can resume through the cache. A different selection under the same wave name or

Every publication rebuilds the global grouping and audit from ALL saved waves:
same-price works may group, different prices and all source occurrences remain.
Interrupted publication recovers locally from the journal before inference.
A lock prevents concurrent campaign writers; a stale lock after a process crash
requires checking that no writer is running before removing that specific lock.
Client folder is an untrusted hint, never proof: harmonization and cross-document
links still require source identity/address evidence. Uncorroborated clients stay
blocked. Ignored/deferred sources are listed with reasons without cloud calls.
Stops the wave on a document failure or consumption limit, saving accumulated
results and producing a paused audit workbook. No next wave is started.
On explicit user instruction, resume with --defer-source "/absolute/failed.pdf"
to leave an already failed PDF pending without deleting it or changing the
approved selection. The original error and deferral are persisted in the wave
cache, campaign journal and workbook audit. Successful documents are not rerun;
the deferral remains effective on later resumes. New/unfailed sources cannot
be deferred through this option.
With explicit user authorization, --continue-on-document-error automatically
defers existing and new document validation failures and PdfReadError failures,
then continues the selection. Deferrals remain persistent with their original
errors and untouched sources. With --continue-on-document-error, every
per-document error (including service, authentication and network errors) is
deferred. Explicit run consumption limits still pause.
Azure OpenAI calls are sequential, with at least 2 seconds between the end of
one SDK call and the start of the next in the same backend/run (including failures).
Time spent on OCR or local processing counts toward this pause; cached LLM results
do not trigger calls or extra waits. Waiting is logged as llm_wait. HTTP 429 alone
allows up to two retries, honoring retry-after-ms or retry-after (seconds or HTTP
date), otherwise waiting 30 then 60 seconds. Delays over 300 seconds pause instead
of retrying early. Each attempt, including rejected requests, consumes the run's
LLM call allowance. SDK internal retries are disabled. Rate limits and retry
decisions are logged as llm_rate_limited. With --continue-on-document-error,
per-document service errors are deferred and processing continues.
Structured documents longer than two selected pages are read in consecutive
blocks of at most two source pages. Normalization is also partitioned by these
blocks. Source page numbers and global OCR table row IDs remain unchanged.
Each completed chunk is privately cached for resume; OCR is reused. Conflicting
metadata and table rows crossing block boundaries are flagged for review.
Chunk-specific cache keys do not invalidate historical small-document results
or completed campaign documents. Additional calls, including retries, remain
subject to the authorized run allowance; a limit pauses rather than skipping data.
55 pages and 32 LLM calls are conservative PER-RUN limits, not EUR limits or
cumulative budgets across restarts. SDK automatic LLM retries disabled.
This selected-page path does not use local-first table routing: at most the
55 selected pages can require Azure OCR, fewer on cache reuse.

Use a fresh output path. This produces a separate diagnostic workbook, never

Structured pipeline (default for CLI run):
1. Full-document OCR, cached independently; table cells retain columns, page regions
   and source spans. No repeat OCR charge when changing reading/normalization.
2. Faithful structured reading of every priced source occurrence; no deduplication.
   Quantity and unit are separate. Missing explicit units remain null in the raw data.
   Project beneficiary and billing recipient have separate corroborating excerpts.
3. Separate normalization request: short complete work names, technical signatures,
   commercial company name and project name, coherent construction lots.
   Normalization cannot modify prices, quantities or totals or remove source lines.
4. Deterministic checks: source evidence, metadata aliases, price-column anchors,
   retained numeric technical characteristics, arithmetic and unit provenance.
   Interpreted units have explicit warnings. Blocking issues are line-specific.
5. Exact grouping by lot, signature, technical numeric features, option, unit,
   exact Decimal price, company, project and year. No price averaging/summing.
   All grouped occurrences retain their own trace rows and base-row references.
   Similar-but-not-identical signatures are not automatically merged.
   Identical verbatim work labels also link groups within those same boundaries,
   even when the model produced different signatures for the repeated source label.
Composite quote lots (plaster/insulation, plumbing/sanitary and masonry) stay
together in the base; the detailed per-line technical trade remains in the audit.

Workbook:
- Base de prix: seven template columns; validated grouped works.
- Traçabilité: every extracted occurrence, billing/project/raw identities,
  unit origin, warnings, cell IDs, technical signature and base-row reference.
- À vérifier: blocking issues only; warnings alone do not exclude a valid work.
- Couverture: detected explicit PU table rows not linked to an extracted line.
  These are possible omissions or OCR/title artifacts, not silently discarded.
  This check does not prove exhaustive coverage of image text outside detected tables.
- Documents ignorés: non-quotes, unsupported files and processing failures.
- Documents: per-file pages, classification, counts, detected priced rows,
  project/billing identities, warnings and failures.
Detected missed table rows are recovered only with explicit designation/PU columns
and valid source spans; ambiguous cells remain in Couverture. Continuation tables
inherit headers only with matching column count/x positions on consecutive pages.
Client identities can be linked across quotes only with an identical beneficiary
address and a corroborating filename; the donor's source, SHA and evidence are
retained and checked when loading the batch. Shared billing addresses do not suffice.
